Курсовой проект

«Технологии разработки и защиты баз данных»

1. Цель
Спроектировать, реализовать и задокументировать защищённую клиент-серверную
информационную систему на базе СУБД. В проекте должны быть продемонстрированы:
анализ предметной области, проектирование БД, серверная логика
(SQL/процедуры/триггеры/транзакции), защита информации, администрирование
(резервное копирование и восстановление), API и клиентский интерфейс,
аналитика/отчёты, тестирование и культура разработки (Git).
2. Конечные результаты (что сдаётся)
1. Работоспособная система (локально либо в контейнерах).
2. Репозиторий Git c историей разработки.
3. Пояснительная записка (структура ниже).
4. Набор тестовых данных и отчётов по тестированию.
5. Полный комплект скриптов БД (создание, миграции, начальное наполнение,
бэкап/restore).
6. Спецификация API (OpenAPI/другой формат), инструкция запуска, руководство
пользователя.
3. Функциональные требования
3.1. База данных
• Минимум 8 таблиц предметной области.
• Нормализация не ниже 3НФ.
• Реальные связи 1:1, 1:М и М:М; внешние ключи, ограничения целостности (NOT
NULL, CHECK, UNIQUE).
• Представления (VIEW) для удобного чтения/отчётности.
• Серверная валидация данных (ограничения, триггеры/процедуры).
3.2. SQL и серверная логика
• Полный CRUD по ключевым сущностям.
• Не менее 3 хранимых процедур (бизнес-операции: расчёты, пакетные изменения и т. п.).
• Функции/триггеры для аудита.
• Транзакции с обработкой ошибок (атомарность бизнес-операций).
• Обработка исключений и возврат человекочитаемых кодов/сообщений на уровень
API.
3.3. Безопасность и администрирование
• Ролевая модель доступа (RBAC), минимум 3 роли (пример: администратор,
пользователь, гость/читатель).
• Хранение паролей в виде безопасного хэша
шифрование/маскирование критичных полей.
• Журнал аудита: кто/когда/что менял (до/после).
• Регламент резервного копирования и восстановление (демонстрация restore на учебном
стенде).
Конфигурация доступа к БД и секретов (env-переменные/конфиг на сервере).
3.4. Клиент-серверное приложение и API
• Клиент (веб или десктоп) с аутентификацией и работой по ролям.

• API (REST или gRPC) для всех основных операций;
спецификация (OpenAPI/описание методов, параметры, коды ошибок, примеры).
• Импорт/экспорт данных: минимум CSV и SQL-скрипты (дамп/миграции).
• Адаптивный интерфейс (не менее 3 брейкпоинтов).
• Настройки пользователя (тема, формат даты/чисел, размер страниц, сохранённые
фильтры) — хранятся на сервере.
• Горячие клавиши (не менее 8) для частых операций.
• Брендбук интерфейса: палитра, шрифты, сетка, иконки; применение единых стилей в
UI.
3.5. Статистика и отчёты
• Подсистема аналитики: сводные таблицы и минимум 2–3
визуализации (диаграммы/графики).
• Фильтры, период, экспорт отчётов в CSV (и/или изображения отчётов).
3.6. Работа с Git
• Публичный или учебный репозиторий (GitHub/GitLab).
• README с инструкцией по запуску (локально/в контейнерах),
описанием архитектуры и ролей.
4. Тестирование (обязательный минимум и артефакты)
• Функциональное: CRUD, поиск/сортировки/фильтры, роли, процедуры/триггеры,
транзакции.
• Интеграционное: взаимодействие сервисов и API, импорт/экспорт.
• Нагрузочное: массовые операции/пакетные транзакции (описать
профиль нагрузки).
• Безопасность: попытки SQL-инъекций, проверка разграничения
прав, корректность шифрования/маскирования.
• Отказоустойчивость: имитация сбоя и восстановление из резервной копии
(подтверждение целостности).
• Автоматизация: unit-тесты серверной логики и/или API; при возможности — запуск
через CI.
• На выходе: тест-план, тест-кейсы, журналы прогонов, отчёт о дефектах, итоговый отчёт.

ВВЕДЕНИЕ
В современном мире рынок детских товаров стремительно развивается, предлагая огромное разнообразие игрушек, которые играют ключевую роль в развитии, обучении и развлечении детей. Однако с ростом ассортимента перед родителями встает сложная задача: выбрать качественные, безопасные и подходящие по возрасту и интересам ребенка товары из тысяч предложений. Существующие онлайн-платформы зачастую не учитывают специфику семейных покупок, где решение принимается совместно родителями и детьми, но с разным уровнем прав и возможностей.
Кроме того, родители сталкиваются с необходимостью контролировать желания ребенка, планировать бюджет, отслеживать новые поступления, а также получать достоверную информацию о товарах. В то же время дети хотят участвовать в выборе, иметь свой "список желаний", но без возможности самостоятельного совершения покупок. Для владельцев бизнеса и менеджеров критически важны инструменты для эффективного управления ассортиментом, заказами и клиентской базой.
В связи с этим особую актуальность приобретает разработка специализированного веб-приложения для магазина игрушек, которое предлагает комплексное решение для всех участников процесса:
Для родителей и детей: Удобный и безопасный совместный шоппинг, где ребенок может формировать свой вишлист, а родитель — одобрять и совершать покупки.
Для покупателей: Широкий каталог с фильтрами, подробными описаниями, отзывами и системой рекомендаций.
Для менеджеров: Полный контроль над товарами, заказами, акциями и клиентскими запросами.
Для администраторов: Управление всей системой, пользователями и критически важными бизнес-процессами.
Таким образом, создание многофункционального веб-сайта для магазина игрушек, ориентированного на потребности всей семьи и обеспечивающего эффективное управление бизнесом, представляется своевременным и востребованным решением.

2.	СПЕЦИАЛЬНАЯ ЧАСТЬ
2.1.	Постановка задачи
Разработать защищенное клиент-серверное веб-приложение для интернет-магазина игрушек, включающее в себя реляционную базу данных, серверную логику на Django REST Framework и адаптивный пользовательский интерфейс, реализующее разграничение функционала по ролям.
2.1.1.	Входные данные
Входные данные представлены в следующем виде:
•	Аутентификационные данные пользователя: Адрес электронной почты, пароль;
•	Персональные данные пользователя: ФИО, адрес электронной почты, пароль, номер телефона, дата рождения.
•	Данные о товаре: название, описание, категория, производитель, цена, количество на складе, фотографии, возрастной рейтинг, характеристики.
•	Данные о заказе: ID пользователя, состав заказа (товары, количество), адрес доставки, статус оплаты, статус доставки.
•	Данные списка желаний (вишлиста): ID пользователя (ребенка), ID товара.
•	Данные отзывов и рейтингов: ID пользователя, ID товара, текст отзыва, оценка (1-5).
2.1.2.	Выходные данные
Выходные данные представлены в следующем виде:
•	Данные пользователя: ID, роль, ФИО, email, пароль, номер телефона, дата рождения;
•	Каталог товаров: Отфильтрованный и отсортированный список товаров с основными атрибутами, включая изображения;
•	Карточка товара: полное описание товара, галерея изображений, отзывы, рейтинг, наличие на складе;
•	Данные заказа: Подтверждение заказа, история заказов пользователя, статус текущих заказов;
•	Список желаний ребенка: Отображается в личном кабинете родителя;
•	Панель управления (для менеджера/администратора): Аналитика продаж, управление товарами, просмотр и обработка заказов.
2.1.3.	Подробные требования к проекту
Необходимо разработать веб-приложение, реализовав в составе него следующие процессы:
•	Проектирование веб-приложения - необходимо спроектировать клиент-серверное веб-приложение, REST API для обеспечения взаимодействия клиентской части с сервером и базой данных. Также, в процессе проектирования необходимо реализовать архитектурную схему приложения, логическую и физическую схему базы данных, функциональную схему, диаграмму классов, схему тестирования и схему пользовательского интерфейса;
•	Проектирование и реализация базы данных – необходимо разработать реляционную базу данных на PostgreSQL, реализующую логику по хранению данных о товарах, пользователях, заказах, категориях, отзывах и списках желаний. База данных должна предусматривать валидацию вводимых данных через ограничения (CONSTRAINTS), а также безопасное хранение паролей учетных записей пользователей с использованием современного алгоритма хеширования (bcrypt);
•	Разработка веб-приложения на базе Django – необходимо разработать клиент-серверное веб-приложение с использованием Django и Django REST Framework, реализующее функции интернет-магазина игрушек с системой ролевого доступа. Приложение должно предусматривать реализацию всех базовых функций, в том числе:
o	Аутентификация и авторизация пользователей с разделением по ролям (неавторизованный пользователь, покупатель, ребенок, менеджер, администратор);
o	Управление каталогом товаров: добавление, редактирование, удаление товаров, управление категориями;
o	Работа с каталогом товаров: просмотр каталога, поиск и фильтрация товаров, добавление в корзину, оформление заказов;
o	Семейный функционал: привязка детских аккаунтов, управление списками желаний (вишлистами);
o	Система отзывов и рейтингов: оценка товаров, написание отзывов;
o	Панель управления: для менеджеров и администраторов - управление заказами, товарами, аналитика продаж;
o	Персонализация интерфейса: переключение между светлой и темной темой приложения;
o	Администрирование: управление пользователями, ролями и системными настройками.
2.2.	Внешняя спецификация
2.2.1.	Описание задачи
Разработать программное решение для автоматизации работы интернет-магазина игрушек с системой семейного шопинга.
Данное программное решение должно состоять из реляционной базы данных под управлением СУБД PostgreSQL и клиент-серверного веб-приложения, реализованного на базе фреймворка Django с использованием Django REST Framework.
Веб-приложение должно предоставлять REST API для взаимодействия клиентской части с сервером и базой данных, а также обеспечивать разграничение функциональности по ролям пользователей.
На этапе анализа были определены основные роли: неавторизованный пользователь, покупатель (родитель), ребенок, менеджер, администратор, и их возможности в системе.
Функциональность по ролям:
Неавторизованный пользователь обладает следующими возможностями:
•	Просмотр каталога товаров;
•	Поиск товаров по названию и описанию;
•	Фильтрация товаров по категориям, возрасту, бренду, цене;
•	Сортировка товаров по цене, популярности, новизне;
•	Просмотр карточек товаров с описанием, изображениями, отзывами;
•	Регистрация в системе в роли "Покупатель";
•	Авторизация в системе.
Покупатель (родитель) обладает следующими возможностями:
•	Все возможности неавторизованного пользователя;
•	Управление личным кабинетом;
•	Редактирование персональных данных;
•	Привязка детских аккаунтов к своему профилю;
•	Добавление товаров в корзину;
•	Просмотр и управление корзиной товаров;
•	Оформление заказов с выбором способа доставки и оплаты;
•	Просмотр истории заказов и их текущего статуса;
•	Написание отзывов и оценка приобретенных товаров;
•	Просмотр "списков желаний" привязанных детей;
•	Добавление товаров из детских вишлистов в корзину.
Ребенок обладает следующими возможностями:
•	Авторизация в системе через привязанный аккаунт;
•	Просмотр каталога товаров;
•	Добавление товаров в персональный "список желаний";
•	Удаление товаров из списка желаний;
•	Просмотр своего вишлиста.
Менеджер обладает следующими возможностями:
•	Управление каталогом товаров (добавление, редактирование, удаление товаров);
•	Управление категориями товаров;
•	Просмотр и обработка заказов (изменение статусов);
•	Просмотр базовой аналитики продаж;
•	Модерация отзывов.
Администратор обладает следующими возможностями:
•	Все возможности менеджера;
•	Полное управление пользователями (назначение ролей, блокировка);
•	Просмотр расширенной аналитики и генерация отчетов;
•	Мониторинг системных журналов.
Дополнительная функциональность системы:
o	Система рекомендаций товаров на основе истории просмотров и покупок;
o	Темная/светлая тема оформления.
